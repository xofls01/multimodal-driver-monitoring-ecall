# 비전과 ECG/PPG 연결

## 이번에 연결한 범위

기존 비전 결과와 전달받은 ECG/PPG 코드를 하나의 재생 시간으로 연결했다. 비전 원본 프로젝트와 드라이브 파일은 수정하지 않았다. 센서 실시간 수신을 새로 구현한 것은 아니며, 현재 입력은 저장된 영상과 CSV다.

N은 센서와 함께 촬영한 20초 정상 기록을 사용한다. 기존 N1 시험 영상과는 다른 영상이다. 원본 `video_overlay.avi`의 위쪽 1280 x 720 카메라 영역 전체를 사용했고, 아래에 이미 붙어 있던 파형 패널만 제거했다. 원본 해상도와 장면의 위아래는 유지한다. 이 영상의 1.5~2.5초를 눈을 뜬 기준 자세 구간으로 검토해 별도 보정 프로필을 추가했다. 이 보정은 실제 도로를 보는 시선의 보정은 아니다.

D3, E4, The new A는 정상 측정 기록을 바탕으로 다시 만든 합성 신호다. 신호 파일의 `session.json`에 생성 방법과 영상 시간이 적혀 있다. 실제 졸음이나 응급 상태에서 측정한 신호로 해석하지 않는다. 파일에 함께 있던 `bio_status.jsonl`과 `vitals.csv`의 정답 또는 결과를 판단 입력으로 사용하지 않았다. `biosignals.csv`의 ECG와 PPG 원시값을 전달받은 모델에 다시 넣었다.

## 모델 연결

비전은 기존 YOLO Pose, YOLO Detection, MediaPipe Face Mesh, MediaPipe Hands와 판단 엔진을 그대로 사용한다. D3, E4, A_new는 직전 휴대전화 오검출 수정 후 실제 분석했던 결과를 원본 영상 SHA256으로 확인해 재사용했다. N의 새 동시 촬영 영상에는 비전을 새로 실행했다. `--fresh-vision`을 지정하면 네 영상 모두 비전부터 다시 실행할 수 있다.

생체신호는 전달받은 `biosignal` 패키지를 `src/biosignal`에 보존해 연결했다. ECG에는 `hr_classifier_ft.pt`, PPG에는 `papagei_s.pt`와 `ppg_head_ft.pt`를 불러온다. 전달받은 `biosignal_camera_live_bpm.py`의 실행 기본값과 동일하게 맞췄다. 추가 학습은 하지 않았다.

생체신호의 심박수는 피크 간격에서 계산한다. `hr_class`는 모델 또는 규칙의 등급이며, 센서 상태와 지속 조건을 거친 최종 생체 등급인 `level`과 다르다. 생체 최종 등급은 받은 `BioSignalMonitor`의 `level`을 그대로 사용한다. 심박수가 없다는 이유로 등급을 다시 분류하지 않는다. 모델 또는 심박 등급인 `hr_class`로 최종 `level`을 덮어쓰지도 않는다. 원래 결과는 `model_reported_level`과 `bio_recomputed.jsonl`에 보존한다.

모델의 학습 자료나 임상 성능은 이번 연결 작업에서 재검증하지 않았다. 공급 코드가 인용한 문헌과 수치는 공급 코드의 설명이며, 이번에 독립적으로 확인한 논문 기준으로 추가한 것이 아니다.

## 시간 연결

`bio clip_s = video seconds + bio_offset_seconds`를 사용한다. 현재 네 쌍의 오프셋은 0초이며 신호 시간을 늘이거나 줄이지 않는다. 시간과 샘플 값은 유한해야 하고, 시간은 증가해야 한다.

D3, E4, A_new의 `frames.csv`가 원본 영상 프레임 수와 FPS에 맞는지 검사한다. 이 세 파일은 합성 자료의 재생 시간 정렬이다. 동시에 수집했다는 의미가 아니다. 일부 `session.json`에 D3나 A인데도 E4라고 복사된 설명이 있어, 그 문구로 매칭하지 않고 실제 프레임 수와 시간표를 검사한다.

N의 원본은 카메라 실측 약 14.51 FPS를 Pi 수신 시각으로 30 FPS, 600프레임에 재배치한 영상이다. `frames.csv`의 290개 시각을 600프레임과 일대일로 대응시키지 않는다. `session.json`의 재배치 정보와 20초 길이를 검사한다. ADC 시각이나 노출 시각이 없어서 USB와 카메라 지연을 보정한 정밀 동기화는 아니다.

생체신호 모델에는 현재 재생 시각 이하의 샘플만 순서대로 넣고 약 1초마다 갱신한다. 미래의 가장 가까운 값으로 메우지 않는다. 그래프도 과거 5초만 그린다. 파일 범위 밖, 수신 공백, 오래된 결과는 판단 불가다. 뒤로 이동하거나 다른 영상을 시작할 때는 분석기를 새로 만든다.

## 통합 판단

비전 상태와 생체 상태를 각각 보존한 뒤 `multimodal_fusion.py`에서 합친다. 이는 연결 가능성을 확인하기 위한 프로토타입 정책이며 검증된 의료 기준이 아니다.

- 비전이 기존 정차 조건으로 Danger를 내면 그 정차 요청을 유지한다.
- 생체 최종 등급이 Danger이고 현재 비전에서 큰 자세 변화가 관측되거나 3초 이상 눈 감김이 관측되면 통합 Danger로 표시한다. 3초는 전달받은 통합 코드의 `sleep_s` 설정을 따른 시험 설정이다. 심정지나 의식 소실 확정이라는 뜻은 아니다.
- 생체 Danger만 있고 뒷받침할 비전 근거가 없으면 Caution으로 두고 추가 확인이 필요하다고 기록한다.
- 어느 한쪽의 유효한 Caution은 다른 쪽의 Normal로 지우지 않는다.
- 비전이 정상이고 생체가 기준선 수집 중이면 통합 Normal을 표시하되 생체는 Unavailable로 별도 표시한다. 모든 센서가 정상이라는 의미가 아니다.
- 비전이 판단 불가인데 심박만 정상이면 운전 상태를 Normal로 만들지 않는다.
- 생체신호의 잡음이나 누락 자체를 Danger 근거로 사용하지 않는다.

현재 비전의 기존 자세 정차 타이머는 유지한다. 같은 큰 자세 변화로 주의가 나온 뒤 3초를 더 관측하면 시뮬레이터 정차를 요청하는 방식이다. 서로 다른 Caution을 단순히 합해 3초를 채우는 방식은 아니다.

전달받은 `fusion` 패키지는 `reference/supplied_fusion`에 보존했다. 현재 연결에는 그 엔진을 그대로 활성화하지 않았다. 기존 비전과 상태 전달 형식이 다르고, 버튼이나 CAN 수신 없이 경고 시간만 흘러도 무응답으로 처리할 수 있기 때문이다. 실제 응답 버튼과 CAN은 연결하지 않았고, 없는 응답을 무응답으로 꾸미지 않는다. rPPG도 독립된 센서 근거로 중복 집계하지 않는다.

## 화면

상단은 통합 상태, 비전 상태, 생체 상태를 따로 보여준다. 영상과 기존 비전의 지속 시간 바는 그대로 유지하고 아래에 ECG와 PPG의 최근 파형, 각 채널의 심박수와 품질, 생체 등급의 근거를 붙였다. 파형의 세로축은 표시된 ADC 범위로 조절되며 두 파형을 합친 임상 파형이 아니다.

녹색은 정상, 노란색은 주의, 빨간색은 정차 요청, 회색은 판단 불가다. 빨간색은 Unity 차량이 실제로 멈췄다는 확인이 아니다. 합성 신호 여부를 상단에 계속 표시한다.

## Unity 전달

분석 중 생성한 현재 `Decision`을 `AnalysisPublisher.publish()`에서 실제 `UnityStateServer.publish()`로 전달했다. `--verify-tcp`는 별도의 로컬 TCP 수신기를 붙여 모든 현재 판단 시각과 상태가 도착했는지 비교한다. Unity 프로그램을 실행한 시험은 아니다.

`vehicle_control` 메시지의 `driver_state`는 Normal, Caution, Danger다. 별도로 `fusion_state`, `fusion_available`, `vision_state`, `vision_available`, `bio_state`, `bio_available`, `bio_source_timestamp`, `bio_age_seconds`, `synthetic_biosignal`, `synchronization`을 보낸다. 생체와 비전의 판단 불가를 일반 주의와 구분한다. 호환용 `driver_state=Caution`만 보지 말고 availability 필드를 함께 사용해야 한다.

전달 결과가 0.75초보다 오래되면 통합 상태와 각 availability를 판단 불가로 바꾸고 정차 요청을 제거한다. 생체신호 결과 자체의 1.5초 유효 시간과 비전 관측의 0.25초 유효 시간도 별도로 검사한다. 서버 heartbeat는 새로운 영상 근거가 아니다.

`integration/Unity/Assets/Stage1BasicVehicle/Scripts/UnityTcpVehicleBridge.cs`에는 통합 availability를 우선 읽는 선택 필드를 추가했다. 기존 비전 메시지도 계속 읽는다. Danger에서 기존 `TriggerEmergency()` 경로로 이어지도록 두었지만 C# 컴파일, Unity UI, 차량 조향, 갓길 정차, e-Call까지 실제 실행해 검증한 것은 아니다.

## 실행

통합 복사본의 최상위 폴더에서 실행한다.

```bash
sh run_multimodal.sh
sh run_multimodal.sh --only E4 --verify-tcp
sh run_multimodal.sh --fresh-vision
```

입력 쌍과 모델 경로는 `config/multimodal/replay_pairs.json`에 있다. 결과는 `outputs/multimodal_bpm/index.html`, 영상은 각 하위 폴더의 `preview.mp4`다. `fusion.jsonl`은 비전, 생체, 통합 결과 전체이고 `bio_recomputed.jsonl`은 원시 신호에서 다시 계산한 결과다. `summary.json`에 프레임 수, FPS, 사용 가중치 해시와 검증 범위를 남긴다.

별도 PC에서는 Python 3.11 가상환경에 `requirements.txt`를 설치한다. 모델과 입력 자료가 포함된 로컬 복사본을 기준으로 경로를 구성했다. 다른 자료를 넣으면 영상 해시와 보정 프로필을 새 자료에 맞춰 검토해야 한다. 기존 프로필을 이름만 바꿔 적용하지 않는다.

실제 Unity에서 저장된 통합 결과를 1배속 시험 재생하려면 다음과 같이 실행한다. 합성 자료의 정차 명령은 명시적인 시험 옵션이 필요하다.

```bash
sh run_multimodal.sh --unity-replay outputs/multimodal_original_bio/E4/fusion.jsonl --allow-synthetic-control
```

이 명령은 TCP 클라이언트 접속을 기다린다. 새로 생성되는 센서 신호를 실시간으로 읽는 명령은 아니다. Unity 긴급 정차 잠금의 해제는 기존 Unity의 명시적인 초기화 기능을 사용한다.

## 남아 있는 확인

새 N 촬영에서는 비전 경고가 일부 발생한다. 카메라 각도와 눈 가시성이 달라 기존 비전의 보정과 눈 감김 판단을 별도로 점검해야 한다. 시나리오 이름이 N이라는 이유로 결과를 강제로 Normal로 바꾸지 않았다.

아래를 보는 장면이 눈 감김으로 읽히는 기존 문제, 합성 E4에 대한 생체 모델의 지연, 접촉 센서가 없는 상태에서의 신호 소실 해석도 남아 있다. 실제 센서 연결과 공통 시각 수집, 가려짐과 잡음 조건, 다른 참가자 자료로 따로 검증해야 한다.

## 이번 실행에서 확인한 결과

총 4개 영상 2,123프레임에서 통합 결과를 계산하고 동일한 시각과 상태가 로컬 TCP 수신기에 도착하는지 확인했다. 비전과 연결부 테스트 208개, 공급 생체신호 코드 테스트 38개가 통과했다. 정상 촬영에 경고가 발생한 것을 정확한 검출이라고 집계하지 않았고, 정확도 지표도 산출하지 않았다.

- N: 20.00초, 600프레임. 통합 결과 unavailable 76프레임, normal 376프레임, caution 148프레임.

- D3: 18.29초, 545프레임. 통합 결과 unavailable 54프레임, normal 321프레임, caution 170프레임.

- E4: 15.84초, 469프레임. 통합 결과 unavailable 32프레임, normal 116프레임, caution 178프레임, danger 143프레임.

- A_new: 17.95초, 509프레임. 통합 결과 unavailable 38프레임, normal 259프레임, caution 212프레임.


E4의 정차 요청은 약 11.01초에 기존 비전의 자세 타이머로 먼저 발생했다. 생체 모델의 위험 결과는 약 12.02초부터였다. 이번 네 자료에서 생체 연결 때문에 경보가 빨라졌다고 결론 내릴 수 없다. D3와 A_new의 정상 심박 결과도 비전 경고를 해제하지 않았다.

## 전달받은 실행 설정 재대조

초기 연결에서는 일반 `hr_classifier.pt`와 `ppg_head.pt`를 선택했다. 공급 실시간 실행 파일의 기본값은 `_ft` 가중치여서 이를 수정했다. 정상 N, D3, E4, A_new 각각에서 일반 가중치와 `_ft` 가중치를 같은 입력과 시간 조건으로 비교했다. 이 자료들의 최종 생체 등급 전환은 같았지만, D3와 A_new에서 PPG 모델 결과를 사용하는 구간은 달라졌다. 화면 상태가 비슷해 보인다고 동일한 모델을 사용했다고 판단하면 안 된다.

받은 `biosignal` 분석 코드와 선택한 가중치는 압축 파일과 바이트 단위로 같고, 입력 CSV 네 개도 드라이브 원본과 같다. 다만 받은 `fusion/FusionEngine` 전체를 실행하는 구조는 아니다. 비전 결과와 생체 `level`을 합치는 연결 규칙은 이 복사본에서 작성했으며, 응답 입력과 CAN이 없는 파일 재생 조건을 명시한다. 공급 프로그램 전체를 변경 없이 실행한 것과 구분해야 한다.

## 측정 준비 표시와 파형 필터 수정

초기 샘플 수집과 기준 심박 수집 중에는 생체 상태 칸에 `MEASURING...`을 표시한다. 기준 수집 시간은 원본 설정의 10초를 읽어 진행 바에 표시한다. 모델 분석과 상태 전송에서는 관측이 충분하지 않다는 기존 의미를 유지하며, 준비 중인 상태를 정상으로 바꾸지 않는다. 신호 불량이나 오래된 결과, 기록 종료는 계속 `UNAVAILABLE`로 구분한다.

분석이 준비되기 전의 기본 SQI 값 0은 측정된 품질로 오해되지 않도록 `--`로 표시한다. 실제 분석에서 측정한 SQI=0은 그대로 표시한다.

화면 파형은 전달받은 `biosignal.dashboard.filtered_waves` 함수를 그대로 사용한다. ECG에는 60 Hz 노치와 0.5~40 Hz 대역통과 및 이동평균, PPG에는 0.5~4 Hz 대역통과와 이동평균이 적용된다. 현재 시점까지 받은 8초를 사용해 여유 구간 3초와 표시 구간 5초를 확보한다. 1.5초보다 짧아 표시용 필터가 준비되지 않았을 때는 준비 문구를 표시하며 원시 파형으로 대체하지 않는다.

이 필터는 화면 표시용이다. CSV 원본, 기존 생체신호 분석, 상태 판단 조건은 수정하지 않았다. 이미 계산한 판단과 Unity 패킷 로그를 그대로 보존해 다시 렌더링했고, 이전 로그와 SHA256이 같은지 검사한다. 화면의 시간축이나 영상 FPS를 바꾸지 않는다. 이 화면 수정에서 새 Unity 실행이나 TCP 통합 시험을 했다는 뜻은 아니다.

`python scripts/rerender_multimodal_display.py --source <기존 결과 폴더> --output <새 결과 폴더>`로 판단을 다시 계산하지 않고 화면만 재생성할 수 있다. `sh run_multimodal.sh`로 전체 분석을 새로 실행해도 같은 표시용 필터가 적용된다.

## 생체 판단 원본 준수 수정

생체신호의 최종 `level`과 `reasons`는 전달받은 알고리즘의 결과를 그대로 전달한다. 심박수 값이 비어 있거나 채널 품질이 낮다는 이유로 원본의 최종 등급을 다시 분류하지 않는다. 이전 연결부의 `NORMAL_WITHOUT_RELIABLE_BPM` 규칙은 제거했다. 영상과 신호의 시간 연결, 결과의 신선도와 기록 범위 확인은 전송 유효성 검사이며 새로운 생체 등급 기준이 아니다.

파일 재생의 1초 갱신 시각도 공급 `tools/replay_recording.py`처럼 첫 샘플 시각에 1초씩 더하는 방식으로 맞췄다. 분석 기준이나 임계값, 모델 가중치는 변경하지 않았다.

전달받은 ZIP에서 분석 소스와 원본 재생 프로그램을 별도로 꺼내 네 CSV를 독립 실행했다. 원본과 수정본의 `BioStatus.to_dict()` 결과 69개가 모든 필드에서 같았다. 영상에 연결된 유효 프레임 2,002개와 Unity 패킷의 생체 등급도 원본 결과와 같았다. 회귀 테스트 223개가 통과했다. 실제 Unity 실행은 하지 않았고 로컬 TCP 시험 수신기로 현재 통합 판단 2,123개의 전달을 확인했다.

E4의 약 10.23초는 원본처럼 생체 `Normal`, 약 12.01초부터는 생체 `Danger`다. `hr_class`가 위험 후보여도 원본의 최종 `level`을 덮어쓰지 않는다. 비전이 주의를 내고 있으면 생체가 정상이더라도 전체 통합 결과는 주의를 유지할 수 있다. 초기 측정 준비 문구와 원본 표시용 파형 필터는 유지한다.

다음 명령으로 원본과의 대조를 재실행할 수 있다. 실행 환경은 프로젝트의 Python 가상환경을 사용한다.

```bash
python scripts/verify_biosignal_reference.py --archive <전달받은 ZIP 경로> --results outputs/multimodal_original_bio
```

자세한 검증 기록은 `outputs/multimodal_original_bio/reference_parity.json`과 `verification.json`에 있다. 이전 단계의 영상과 검증 기록은 각 이전 outputs 폴더에 보존한다.

## 생체 화면 간소화

생체 화면은 상단의 생체 상태, 큰 심박수, 경고 또는 측정 준비 중의 짧은 이유만 표시한다. 정상일 때 추가 설명을 붙이지 않는다. 원본 등급과 이유 코드는 로그에 그대로 남기고 화면의 문구만 줄였다. 모델 이름, SQI 숫자, 필터와 축 범위 설명, 내부 통합 규칙 이름, CAN과 rPPG 연결 설명은 영상에서 제외했다. 합성 신호 표시는 상단에 작게 유지한다.

비전의 시간 바와 반복 횟수는 그대로다. 카메라 영역도 1280 x 720 전체를 유지하고 설명 문장을 없앤 아래 패널만 줄였다. 원본 생체 판단 코드와 가중치는 바이트 단위로 같고, `biosignal.dashboard.filtered_waves`를 직접 호출한다. 최신 화면은 `outputs/multimodal_bpm/index.html`에서 확인한다. 이전 원본 대조 결과는 `outputs/multimodal_original_bio/reference_parity.json`에 보존한다.

## BPM 표시와 생체 판정의 준비 시간을 분리

원본 `biosignal.dashboard.summarize`는 `status.level`이 측정 준비 중이어도 `status.hr`이 있으면 BPM을 표시한다. 통합 UI가 `bio.available`로 BPM까지 숨기던 조건을 제거했다. 이제 원본 분석기의 현재 HR을 최종 등급과 관계없이 표시한다.

분석값이 아직 없는 초기 구간에는 같은 촬영 폴더의 `vitals.csv`에서 이미 계산해 저장한 BPM을 표시하고 숫자 옆에 `Recorded`를 붙인다. 현재 재생 시각 이하의 가장 최근 행만 사용하며, 유효한 `hr_src`와 양수 HR이 있는 현재 값만 쓴다. 처음 약 0.57초의 기록이 도착하기 전에는 미래 값을 당겨 쓰지 않는다. 새 행이 HR 소스 없음 또는 값 없음으로 바뀌면 이전 숫자를 계속 유지하지 않는다. 오래된 값은 표시하지 않는다.

원본 분석기의 HR이 확보되면 그 값을 우선한다. N은 약 0.6초부터 저장 BPM을 표시하고 약 6초부터 원본 분석 HR을 표시한다. 원본의 10초 개인 기준 수집 조건은 유지하므로 BPM 숫자와 `MEASURING...`이 동시에 나올 수 있다. 원본 녹화 화면에 이미 표시된 Nano BPM과, 클립 첫 시점부터 다시 시작한 파이썬 분석 결과의 준비 시간은 다르다.

`vitals.csv`는 숫자 표시용으로만 연결했다. `BioSignalMonitor` 입력이나 최종 생체 등급, 비전 통합 판단에는 넣지 않는다. 생체 원본 분석 결과 69개와 유효 프레임 및 패킷의 생체 등급 2,002개는 이전과 같고 원본과도 일치한다. UI에 사용한 수치, 출처, 해당 값의 시각은 각 영상의 `display_bpm.jsonl`에 따로 남긴다. D3, E4, A의 vitals 또한 제공받은 합성 자료의 기록값이며 실제 응급 상태의 측정값이 아니다.

E4 후반처럼 원본 분석과 저장 파일 모두에 유효한 BPM이 없을 때는 `--`를 유지한다. 값을 만들거나 0 BPM으로 바꾸지 않는다. 표시용 파형 필터도 계속 전달받은 원본 함수를 호출한다.
